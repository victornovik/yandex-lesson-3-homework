**Общая идея.** Новый функционал по открытию депозитов выносится в отдельные микросервисы рядом с интернет-банком. С АБС они общаются только асинхронно через Kafka. Таким образом заявки принимаются, даже если АБС недоступна или перегружена, а БД АБС не получает прямую нагрузку от клиентов.

**Обоснование принятых решений**

- **R4, P2, ограничение АБС.** Прямые вызовы API или БД АБС из интернет-банка должны быть исключены. Заявки идут через Kafka и адаптер, который ограничивает скорость записи в Oracle. Ставки реплицируются из АБС в сервис ставок.
- **S2 и +R2.** Ядро интернет-банка на .NET Framework 4.5 с Kafka несовместимо, поэтому Kafka используют только новые микросервисы на .NET Core 10.0. Микросервисы вызываются через API Gateway по REST, монолит с ними напрямую не связан.
- **S1.** БД новых сервисов — MS SQL (есть в банке), АБС — Oracle. Новые технологии: Kafka и современный .NET Core 10.0 (для микросервисов, команда знает C#). Для адаптера выбран Java, потому что в команде АБС есть Java-специалисты.
- **S4.** Ядро интернет-банка не дорабатывается: СМС-код отправляет существующий функционал, новый код живёт в микросервисах и React-фронтенде. Клиент не обращается к монолиту напрямую: все запросы проходят через API Gateway.
- **R1, R2, R3.** Микросервисы и адаптер масштабируются горизонтально за балансировщиком. Kafka и сервисы развёрнуты в обоих ЦОД, при сбое трафик переключается на резервный. АБС масштабируется только вертикально, поэтому её разгружает коммуникация через message broker.
- **R5.** TLS между клиентом, фронтендами и API Gateway, а также между сервисами. Сайт не хранит ПДН, заявка сразу уходит в систему кол-центра.
- **F3.** Ставки и согласование переходят из Эксель файлов в АБС. Для депозитов и кредитов заведены разные роли.
- **P1.** Ставки читаются из кеша сервиса ставок, а не из медленных справочников монолита.
- **Единая точка входа.** Клиент открывает сайт или веб-интерфейс интернет-банка, а запросы к бэкенду идут через API Gateway.

**Недостатки, ограничения, риски**

- **Эксплуатация Kafka.** В банке нет опыта, нужны обучение и подготовка команды эксплуатации. Кластер в двух ЦОД требует отдельного проектирования.
- **Консистентность.** Ставки реплицируются, поэтому возможна задержка. Нужны идемпотентность и deduplication.
- **Интеграция с кол-центром.** Новый endpoint в системе подрядчика создаёт зависимость от подрядчика и ресурсов специалистов АБС.
- **Много разнородных технологий в одной архитектуре.** .NET Framework 4.5 (ядро), современный .NET Core(микросервисы), Java (адаптер), PL/SQL, Delphi, MS SQL. Повышает сложность сопровождения и требует хорошей документации.
- **Сроки.** MVP за 6 месяцев при участии нескольких команд. Риск в согласовании интерфейсов и возможных переделок из-за неучтенки.
- **Нагрузка на АБС.** Даже с ограничением скорости запись заявок добавляет работу к перегруженной БД. Нужны нагрузочное тестирование и мониторинг.
- **Идентификация нового клиента.** Заявка с сайта не завершается онлайн, клиент должен все равно лично прийти в отделение.
