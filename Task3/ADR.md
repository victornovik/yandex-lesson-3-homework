**Общая идея.** Новый депозитный функционал выносится в отдельные микросервисы рядом с интернет-банком. С АБС они общаются только асинхронно через Kafka. Так заявки принимаются, даже если АБС недоступна или перегружена, а БД АБС не получает онлайн-нагрузку от клиентов.

**Логика принятых решений**

- **R4, P2, ограничение АБС.** Прямой вызов API или БД АБС из интернет-банка убран из нового процесса. Заявки идут через Kafka и адаптер, который ограничивает скорость записи в Oracle. Ставки реплицируются из АБС в сервис ставок.
- **S2 и +R2.** Ядро на .NET Framework 4.5 с Kafka несовместимо, поэтому Kafka используют только новые микросервисы. Ядро вызывает их по REST. Обновление ядра на современный .NET выносится за рамки MVP.
- **S1.** Хранилища новых сервисов — MS SQL (есть в банке), АБС — Oracle. Новые технологии: Kafka (требование) и современный .NET (для микросервисов, команда знает C#). Для адаптера выбран Java, потому что в команде АБС есть Java-специалисты.
- **S4.** Ядро интернет-банка не дорабатывается: СМС-код отправляет существующий функционал, новый код живёт в микросервисах и React-модуле.
- **R1, R2, R3.** Микросервисы и адаптер масштабируются горизонтально за балансировщиком, Kafka и сервисы развёрнуты в обоих ЦОД, при сбое трафик переключается на резервный. АБС остаётся вертикально масштабируемой, поэтому её разгружает очередь.
- **R5.** TLS между клиентом и балансировщиком, а также между сервисами. Сайт не хранит персональные данные, заявка сразу уходит в систему кол-центра.
- **F3.** Ставки и согласование переходят из XLS в АБС. Для депозитов и кредитов заведены разные роли. Кредитный отдел вносит показатели риска в свой раздел, менеджер депозитов видит только агрегированный показатель.
- **P1.** Ставки читаются из кеша сервиса ставок, а не из медленных справочников ядра.

### **Альтернативы**

| Альтернатива                                                   | Почему отклонена                                                                                                   |
| :------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------- |
| Интернет-банк пишет заявки напрямую в АБС (как платежи сейчас) | БД АБС перегружена и масштабируется только вертикально. Доступность интернет-банка связана с АБС. Нарушает R4 и P2 |
| Реализовать депозиты внутри монолита интернет-банка            | Нужны доработки ядра подрядчиком (против S4), нет Kafka (+R2), сложнее масштабировать                              |
| Сначала обновить ядро интернет-банка на современный .NET       | Дорого, не уложится в MVP за 6 месяцев. Откладывается на второй этап                                               |
| Очередь RabbitMQ или таблицы-очереди в БД вместо Kafka         | Требование: Kafka на перспективу                                                                                   |
| Реализовать новые сервисы на Java                              | В банке большая экспертиза .NET в команде интернет-банка. Java используется только для адаптера АБС                |
| Сайт подаёт заявку сразу в АБС или интернет-банк               | Заявку должен увидеть менеджер кол-центра, поэтому она идёт в систему кол-центра                                   |

**Недостатки, ограничения, риски**

- **Асинхронность.** Статус заявки обновляется с задержкой. Клиенту нужен понятный статус «Принята».
- **Эксплуатация Kafka.** В банке нет опыта, нужны обучение и подготовка команды эксплуатации. Кластер в двух ЦОД требует отдельного проектирования.
- **Консистентность.** Ставки реплицируются, поэтому возможна задержка. Нужны идемпотентность и контроль дублей.
- **Резервный ЦОД.** Команда интернет-банка считает R2 пока невыполнимым. Нужно подтвердить возможность переключения ядра, при необходимости ограничиться деградацией (ядро в одном ЦОД, новые сервисы в двух).
- **Интеграция с кол-центром.** Новый endpoint в системе подрядчика создаёт зависимость от подрядчика и ресурсов специалистов АБС.
- **Много технологий в одном процессе.** .NET Framework 4.5 (ядро), современный .NET (микросервисы), Java (адаптер), PL/SQL, Delphi. Повышает сложность сопровождения и требует документации.
- **Сроки.** MVP за 6 месяцев при участии нескольких команд. Риск в параллельности работ и согласовании интерфейсов.
- **Нагрузка на АБС.** Даже с ограничением скорости запись заявок добавляет работу к перегруженной БД. Нужны нагрузочное тестирование и мониторинг.
- **Идентификация нового клиента.** Заявка с сайта не завершается онлайн, клиент должен прийти в отделение: это ограничение регулятора.
- **Партнёрский кол-центр** в MVP не участвует.
